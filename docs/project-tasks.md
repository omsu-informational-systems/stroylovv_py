## 2. Подробное описание задач

### TASK-01: Подключение к брокеру Kafka по протоколу SASL_SSL / SCRAM-SHA-256
* **Описание:** Настроить клиентскую библиотеку `aiokafka` для установления защищенного асинхронного соединения со стендом платформы (`omsu.7bits.it:9094`). Вынести адрес брокера, учетные данные и параметры TLS в конфигурацию.
* **Ожидаемый результат:** Экземпляры `AIOKafkaProducer` и `AIOKafkaConsumer` успешно проходят аутентификацию по механизму SCRAM-SHA-256 и проверяют доверенный TLS-сертификат сервера.
* **Критерии готовности:**
  1. Адрес брокера, порт, протокол и уникальный `KAFKA_GROUP_ID` вынесены в `.env` и загружаются через класс `Settings`.
  2. Пароль `KAFKA_PASSWORD` не зашит в исходный код и не попадает в публичные журналы и Git.
  3. Проверка TLS-сертификата сервера `omsu.7bits.it` включена по умолчанию.

### TASK-02: Регистрация сервиса на платформе (`account.registration.request` / `account.registration.result`)
* **Описание:** При старте сервиса автоматически отправлять событие регистрации в топик `account.registration.request` со стабильными идентификаторами студента (`accountName`), учебной группы (`groupId`), стратегии (`strategyName`) и сервиса (`serviceName`), а также переданным ключом `secretKey`. Реализовать асинхронную обработку ответа `account.registration.result`.
* **Ожидаемый результат:** Платформа отображает студента, группу, сервис и стратегию. При отказе платформы в регистрации сервис фиксирует понятную причину и полностью блокирует отправку рекомендаций.
* **Критерии готовности:**
  1. JSON-сообщение содержит общую структуру платформы и поле `schemaVersion: "1.0.0"`.
  2. В поле `secretKey` отправляется выданный ключ (логин), а не секретный пароль.
  3. Повторный запуск сервиса использует идентичные параметры и не дублирует учетную запись студента.
  4. При получении события `account.registration.result` с отказом (`success: false`) сервис записывает структурированный лог с причиной и не публикует рекомендации.

### TASK-03: Потребление потока свечей (`market.candle.closed`)
* **Описание:** Настроить чтение закрытых свечей из топика `CANDLE_TOPIC` (по умолчанию `market.candle.default`). Реализовать десериализацию сообщений с валидацией инвариантов цен (`High >= Low`, `Open`, `Close` > 0).
* **Ожидаемый результат:** Сервис непрерывно принимает поток событий `market.candle.closed`, десериализует их в доменные сущности `Candle` и передает в юзкейс обработки.
* **Критерии готовности:**
  1. Консьюмер использует уникальный `group.id` для сервиса студента (`candles-student-key-05`), гарантируя получение полной копии потока.
  2. Поддерживаются форматы с плоской структурой и вложенным объектом `candle`/`data`.
  3. Каждая свеча логируется со структурированными полями: тикер, время, цена закрытия, объём, партиция и смещение (offset).
  4. Реализован ручной коммит смещения (At-Least-Once) только после завершения цикла обработки.

### TASK-04: Публикация базовой торговой рекомендации `HOLD` (`strategy.recommendation.created`)
* **Описание:** Обеспечить отправку торговой рекомендации `HOLD` при начальном заполнении скользящего окна либо при нахождении котировки внутри ценового диапазона, а также при фиктивных свечах выходных дней.
* **Ожидаемый результат:** В топик `strategy.recommendation.created` публикуются валидные JSON-сообщения со статусом `HOLD`, границами канала Donchian и нулевой уверенностью (`confidence: 0.0`).
* **Критерии готовности:**
  1. Сообщение содержит поле `schemaVersion: "1.0.0"`, `secretKey`, `serviceName`, `ticker`, `timestamp`, `signal: "HOLD"`.
  2. Рекомендации отправляются с ключом партиционирования по тикеру инструмента.
  3. При отклоненной регистрации отправка рекомендаций `HOLD`/`BUY`/`SELL` блокируется до устранения ошибки.

### TASK-05: Реализация алгоритмической стратегии (Пробой каналов Дончяна и Гибридный ансамбль)
* **Описание:** Реализовать доменные модели стратегий:
  - Базовый пробой 20-периодного диапазона Donchian Channels (`Close > Upper` -> `BUY`, `Close < Lower` -> `SELL`).
  - Гибридный мульти-активный ансамбль: статистический арбитраж на банковском спреде (`SBER` + `T`) с двойным подтверждением тренда + ростовой моментум `OZON` с фильтром объёма.
* **Ожидаемый результат:** Высокая доходность и минимальная просадка при торговле российскими акциями, подтвержденная бэктестом на мок-портфеле (Win Rate 75%, Profit Factor 11.61, MDD 0.27%).
* **Критерии готовности:**
  1. Доменный слой изолирован от сторонних библиотек (0 third-party imports, чистый Python).
  2. Все параметры стратегии (окна, коэффициенты Z-score, множители объёма) передаются из `.env`.
  3. Наличие защиты от «пурпурной стены» выходных дней (`volume <= 0` или `High == Low` -> `HOLD`).

### TASK-06: Отказоустойчивость брокера, авто-реконнект и структурированное логирование
* **Описание:** Обеспечить устойчивость сервиса к сетевым сбоям, недоступности или перезапуску брокера Apache Kafka. Настроить структурированное логирование жизненного цикла.
* **Ожидаемый результат:** При падении или перезапуске брокера Kafka микросервис не падает с ошибкой, а входит в цикл ожидания и автоматически восстанавливает соединение и подписку.
* **Критерии готовности:**
  1. Остановка брокера не завершает процесс FastAPI приложения.
  2. При восстановлении брокера консьюмер и продюсер автоматически возобновляют работу без ручного вмешательства.
  3. HTTP-эндпоинт `GET /health` корректно отражает статус доступности брокера (`UP` / `DEGRADED`).
